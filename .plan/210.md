# Plan — #210 Sidebar nav labels flicker between locale variants on navigation

- **Status:** draft (pending product-lead approval)
- **Type / priority / estimate:** bug · P1 · ~2–3h
- **blocked_by:** none

## Problem restated

The sidebar `nav.*` labels and the logout label alternate between the Spanish
and English renderings depending on load timing:

- ES render: `nav.dashboard` → "Panel de Control", `nav.logout` → "Cerrar sesión"
- EN render: `nav.dashboard` → "Dashboard", `nav.logout` → "Logout"

Both locale files are complete (`apps/app/src/i18n/locales/{es,en}.json` carry
every `nav.*` key), so this is **not** a missing-key / fallback-chain bug. The
labels swap wholesale because the **active resolved locale is not deterministic
at first paint** — react-i18next mounts and paints before i18next has settled on
a language, then re-renders when i18next fires `initialized` / `languageChanged`.
Whichever value wins the first microtask is what the user briefly sees, and a
route navigation that coincides with that settle surfaces the flip.

> Note: the production observation (2026-06-05) reported a title-cased "Cerrar
> Sesión", which matches **no current locale value** (es is lowercase "Cerrar
> sesión", en is "Logout"). See Risks — confirm the live bundle is current before
> attributing the prod symptom solely to this race.

## Root cause (to confirm during implementation)

`apps/app/src/main.tsx` imports `./i18n` (which calls `i18n.use(LanguageDetector)
.use(initReactI18next).init(...)` returning a Promise) and then **immediately**
calls `createRoot(...).render(<App/>)` without awaiting that init Promise. Even
though `apps/app/src/i18n/index.ts` sets `initImmediate: false` (and #187 added
`supportedLngs` + `load: 'languageOnly'` + localStorage-before-navigator order),
React mounts while i18next is still resolving the detected locale. The
`useTranslation()` hook in `AppLayout` subscribes to i18n events and re-renders
on `initialized`/`languageChanged`, so the first paint can show `fallbackLng`
('es') and a subsequent tick flips to the detected locale ('en'), or vice versa.
There is also a non-React consumer reading the locale directly
(`apps/app/src/lib/appointment-api.ts` reads `i18n.resolvedLanguage`/`i18n.language`),
which is the surface #187 tried to keep in sync — reinforcing that a settled,
deterministic locale before render is the right fix point.

## Approach

1. **Reproduce & confirm the race.** Run the app, hard-reload `/` several times
   with `localStorage.language` unset and with a non-`es` navigator locale, and
   watch the sidebar for the EN↔ES flip on first paint. Confirm whether the flip
   is a first-paint re-render (race) vs. a stale value.
2. **Gate the React render on i18next readiness (primary fix).** Export the init
   Promise from `apps/app/src/i18n/index.ts` and have `main.tsx` await/`.then()`
   it before `createRoot(...).render(...)`. This guarantees `i18n.language` /
   `resolvedLanguage` and `document.documentElement.dir`/`lang` are settled
   before the first paint, so every `t('nav.*')` and `t('nav.logout')` resolves
   against one consistent locale. Keep `initImmediate: false`.
3. **Defensive readiness gate in the layout (secondary, optional).** As belt-and
   -suspenders, gate `AppLayout` (or a small root wrapper) on react-i18next
   `ready` so the nav never paints against an unsettled locale even if the root
   gate is bypassed. If using the `ready` flag, set `react: { useSuspense: false }`
   in the i18n config so `useTranslation().ready` is meaningful without a Suspense
   boundary; otherwise wrap in `<Suspense>`. Prefer the smallest change that makes
   the test pass — likely the root gate alone is sufficient.
4. **Verify across locales.** Confirm ES/EN/AR (including AR RTL via
   `updateDocumentDirection`) all render a single consistent label set on first
   paint and after navigating between every section.

## Affected areas

- `apps/app/src/main.tsx` — await/gate `createRoot().render()` on the i18n init
  Promise so the language is settled before first paint.
- `apps/app/src/i18n/index.ts` — export the init Promise (the `i18n.init(...).then(...)`
  chain) for `main.tsx` to await; optionally add `react: { useSuspense: false }`
  if the layout uses the `ready` flag. Keep existing detection config intact.
- `apps/app/src/components/layout/AppLayout.tsx` — (optional) defensive `ready`
  gate before rendering the sidebar nav / logout button; no change if the
  root-level gate fully resolves the race.
- `apps/app/src/i18n/i18n.test.ts` — extend with a test asserting deterministic
  resolution at init (and that the init Promise is awaitable).
- New/updated render test for `AppLayout` (e.g. alongside existing component
  tests) asserting nav labels render a single consistent locale once i18n is
  ready.

## Acceptance criteria

- [ ] Root cause identified and documented: the same `nav.*`/`nav.logout` keys
      resolve to different values across renders because the resolved locale is
      not settled before first paint (React renders before i18next init resolves).
- [ ] The resolved locale is stable before the layout renders (render gated on
      i18n readiness), OR all `nav.*` keys are guaranteed to resolve to a single
      consistent value on first paint.
- [ ] Sidebar nav labels and the logout label are identical across all sections
      on first paint and remain consistent after navigating between sections —
      verified in ES, EN, and AR (with AR confirming RTL `dir`/`lang` set before
      paint).
- [ ] No flash of `fallbackLng` ('es') values when the detected/saved locale is
      'en' or 'ar' (and vice versa).
- [ ] Existing i18n behavior preserved: localStorage-before-navigator detection,
      `supportedLngs`, `load: 'languageOnly'`, and the non-React consumer in
      `lib/appointment-api.ts` continue to read a consistent resolved locale.

## Risks / open questions

- **Stale-bundle vs. code race.** The reported title-cased "Cerrar Sesión"
  matches no current locale string, and project memory notes prior prod
  "flicker/stuck" reports that were stale-deploy artifacts. The implementer
  should confirm the flip reproduces on a fresh hard-reload of the **current**
  bundle before/after the fix; if it only appears on stale cached bundles, the
  deterministic-settle fix is still correct but the prod symptom may additionally
  need a cache-bust/redeploy re-verification (out of scope for the code change).
- **Startup delay.** Gating render on the init Promise adds at most a microtask
  delay since all resources are bundled inline — negligible, but verify no blank
  flash is introduced (add a minimal fallback if needed).
- **StrictMode double-invoke.** `main.tsx` renders under `<StrictMode>`; ensure
  the gating wrapper does not double-create the root or double-fire init.
- **Suspense vs. `ready` flag.** If the optional layout gate uses
  react-i18next `ready`, `react: { useSuspense: false }` must be set or a Suspense
  boundary added; choose one to avoid an unhandled Suspense in tests.
- **Scope discipline.** Keep the change to render-ordering / readiness gating; do
  not alter detection order, locale strings, or the #187 non-React sync surface
  beyond what is needed to settle the locale before paint.
