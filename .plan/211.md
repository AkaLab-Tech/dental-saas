# Plan — #211 Month label capitalized as "Junio De 2026" in the appointments calendar

- **Status:** draft (pending product-lead approval)
- **Type / priority / estimate:** bug · P1 · ~1h
- **blocked_by:** none

## Approach

The reported defect is a CSS title-casing bug: the Tailwind `capitalize` class uppercases
**every** word of an already-localized Spanish date string, so the connector "de" becomes
"De". The correct fix is `first-letter:uppercase`, which sentence-cases only the leading
letter and leaves the in-string "de" lowercase.

Key finding from `git blame` / `git show 8f00fe8`: the **literal** header named in the task —
the month-year `<h2>` at `apps/app/src/pages/appointments/AppointmentsPage.tsx:292` — was
**already fixed** by PR #191 ("fix(app): correct currency formatting and month-year
capitalization", commit `8f00fe8`, dated 2026-06-05). That commit switched
`capitalize` → `first-letter:uppercase` on exactly this element, producing "Junio de 2026".
The production sighting on 2026-06-05 was on the pre-#191 deploy (stale-deploy pattern noted
in project memory), not a live code defect on `main`.

However, the **same root-cause bug is still live** in the same calendar view, one element down:
the per-day group header `<h3>` at line **409** still carries the `capitalize` class. It renders
`formatDateHeader(date)`, which for a normal date returns the localized
`{weekday:'long', day:'numeric', month:'long'}` string — e.g. Spanish "lunes, 5 de junio" —
so `capitalize` turns it into "Lunes, 5 **De** Junio". This is the identical "De" defect the
task describes, just on the day header rather than the month header. Completing #191's fix here
is the actionable core of this task.

Order of work:

1. Apply the same fix #191 used to the day-group header: replace `capitalize` with
   `first-letter:uppercase` at line 409. Spanish day headers then read "Lunes, 5 de junio".
2. Confirm (no change expected) that the month-year `<h2>` at line 292 already reads
   "Junio de 2026" via `first-letter:uppercase`.
3. Resolve the locale inconsistency that the "verify EN/AR" criterion exposes (see Risks):
   `formatMonthYear` (line 210) hardcodes `'es-ES'` while `formatDateHeader` (line 225) uses
   `i18n.language`. Recommended minimal change: switch `formatMonthYear` to `i18n.language` so
   the month-year header is localized for EN/AR like the day header already is. This is a
   product-lead decision (see open questions) — it is a behavioral change beyond pure casing.
4. Add a regression test in `AppointmentsPage.test.tsx` (currently no test pins the casing) that
   asserts the header text renders sentence-cased with a lowercase connector ("Junio de 2026" /
   "5 de junio"), so the `capitalize` regression cannot silently return.

## Affected areas

- `apps/app/src/pages/appointments/AppointmentsPage.tsx` — line 409: `capitalize` →
  `first-letter:uppercase` on the day-group `<h3>`. Line 292 `<h2>` already correct (verify only).
  Line 210 `formatMonthYear`: optionally swap hardcoded `'es-ES'` for `i18n.language` (pending
  the open question below).
- `apps/app/src/pages/appointments/AppointmentsPage.test.tsx` — add a regression assertion for
  the rendered month-year / day-header casing in Spanish (and ideally EN/AR).

## Acceptance criteria

- [ ] The Spanish month-year header reads "Junio de 2026" (no capital connector). Already shipped
      via #191 on `main`; confirm it renders correctly and is covered by a regression test.
- [ ] The Spanish day-group header reads "…, 5 de junio" — the remaining live `capitalize`
      instance at line 409 is fixed to `first-letter:uppercase` ("De" → "de").
- [ ] EN and AR appointment-calendar headers are verified unaffected/correct (no broken casing;
      decide and apply whether the month-year header should localize via `i18n.language`).
- [ ] A regression test asserts the sentence-cased, lowercase-connector output so the bug
      cannot silently return.

## Risks / open questions

- **The headline defect is already fixed on `main`.** The task title points at the month-year
  `<h2>`, which #191 already corrected. The product lead should confirm the intended scope of
  #211 is now (a) closing out the identical remaining instance on the day-group header (line 409)
  and (b) adding the missing regression coverage — rather than re-fixing something already shipped.
  If the lead considers #211 satisfied by #191, this task may instead just need a regression test
  plus a prod re-verify after deploy.
- **Locale inconsistency / EN-AR question.** `formatMonthYear` hardcodes `'es-ES'`, so EN/AR
  users currently see the month-year in Spanish regardless of UI language, while the day header
  (`formatDateHeader`) already follows `i18n.language`. Switching `formatMonthYear` to
  `i18n.language` makes EN render "June 2026" and AR the Arabic month — correct and consistent,
  but it is a behavioral change beyond the cosmetic casing fix. Decision needed: include this
  localization fix in #211, or keep #211 strictly to casing and file the locale fix separately?
- **`first-letter:uppercase` and RTL/Arabic.** Arabic has no letter-casing, so the utility is a
  no-op there (safe). For EN the leading letter is already uppercase from `toLocaleDateString`,
  so the utility is harmless. No locale regression expected, but EN/AR should be visually verified.

Scope confirmed to INCLUDE the `formatMonthYear` localization fix (`es-ES` → `i18n.language`) as part of #211 — the hardcoded `es-ES` is exactly why EN/AR users see the month in Spanish, which the "verify EN/AR" acceptance criterion requires. The already-shipped h2 (fixed by #191) is NOT re-touched; work targets the line-409 h3 instance + regression test + the locale fix.
