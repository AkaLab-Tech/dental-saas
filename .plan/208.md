# Plan — #208 Dashboard stats `401` race on a fresh login

- **Status:** draft (pending product-lead approval)
- **Type / priority / estimate:** bug · P1 · ~1h
- **blocked_by:** none

## Approach

The axios request interceptor (`apps/app/src/lib/api.ts:18-31`) attaches the
`Authorization: Bearer <accessToken>` header by reading
`useAuthStore.getState().accessToken` **at request time** — so a stats request
only 401s when that token is still `null` at the moment the request fires. The
race lives entirely in the trigger, not the interceptor.

`DashboardPage` (`apps/app/src/pages/dashboard/DashboardPage.tsx:98-102`) fires
`fetchAllStats()` from a mount `useEffect` whose only guard is `!isDoctorOrStaff`:

```tsx
useEffect(() => {
  if (!isDoctorOrStaff) {
    fetchAllStats()
  }
}, [fetchAllStats, isDoctorOrStaff])
```

`fetchAllStats()` (`stats.store.ts:133-162`) fans out the four `/stats/*`
requests (`overview`, `appointments`, `revenue`, `patients-growth`) via
`Promise.all`. When the dashboard mounts before the store's `accessToken` has
been committed/observed, all four go out unauthenticated → four `401`s in the
console, and the cards fall back to the `|| 0` / empty-array defaults until the
next render attaches the token and the dashboard recovers.

**Minimal fix — gate the fetch on auth-ready state (token attached):** read
`accessToken` from the auth store the component already imports and only fire
`fetchAllStats()` once a token is present, with `accessToken` in the dependency
array so the effect re-runs and fetches the instant the token lands:

```tsx
const { user, accessToken } = useAuthStore()
// ...
useEffect(() => {
  if (!isDoctorOrStaff && accessToken) {
    fetchAllStats()
  }
}, [fetchAllStats, isDoctorOrStaff, accessToken])
```

This matches acceptance criterion #1's "gate before firing" option, is a 2-line
change, needs no new store/interceptor state, and preserves the existing
`isLoading && !overview` spinner so the first paint shows the loader (not zeroed
cards) until real data arrives.

`DoctorDashboard` (`DoctorDashboard.tsx:96-104`) has the same unguarded
mount-fetch pattern (it fires five `/stats/*` calls via `fetchMyDoctorId` →
`fetchDoctorStats`), so DOCTOR/STAFF users hit the same race. The task's
acceptance is scoped to the four admin stat cards, but applying the identical
`accessToken` guard there is a near-zero-cost parallel fix — see open questions.

## Affected areas

- `apps/app/src/pages/dashboard/DashboardPage.tsx` — destructure `accessToken`
  from `useAuthStore()`; add `&& accessToken` to the effect guard and
  `accessToken` to the dependency array. (Required.)
- `apps/app/src/pages/dashboard/DoctorDashboard.tsx` — same `accessToken` guard
  on its `loadDoctorStats` effect. (Recommended; in scope if we fix the race
  for all roles, otherwise defer — see open questions.)
- `apps/app/src/pages/dashboard/DashboardPage.test.tsx` — the existing test
  mocks `useAuthStore`; add/adjust a case so the mocked store returns an
  `accessToken` (existing happy-path cases must set it, or `fetchAllStats` will
  no longer be called) plus a new case asserting `fetchAllStats` is **not**
  called when `accessToken` is `null`. (Test-owner work; flagged for the tester.)

## Acceptance criteria

- [ ] The stats requests are gated on the auth-ready state — `DashboardPage`
      only calls `fetchAllStats()` once the access token is present in the auth
      store, and re-runs to fetch the moment the token is attached (token in the
      effect dependency array).
- [ ] A fresh login (right after register or login) shows **no** `401`
      responses for `/api/stats/overview`, `/revenue`, `/patients-growth`, or
      `/appointments` in the browser console.
- [ ] On a fresh login the dashboard cards populate with real data on first
      paint (the loading spinner shows until data arrives; no flash of empty/zero
      cards), verified end-to-end with the Playwright MCP.

## Risks / open questions

- **DoctorDashboard scope:** the four-card acceptance is admin-only, but the
  same race exists for DOCTOR/STAFF via `DoctorDashboard`. Recommendation: fix
  both in one PR (the guard is identical and trivial) so we don't leave a known
  sibling bug. Product lead to confirm including it, or split it to a follow-up.
- **Test fragility:** existing `DashboardPage.test.tsx` happy-path cases mock
  `useAuthStore` and will stop calling `fetchAllStats` unless they now provide a
  non-null `accessToken`. The tester must update those mocks alongside the new
  "no token → no fetch" assertion; this is expected, not a regression.
- **Root-cause confirmation:** the interceptor reads the token at request time,
  so within a single tab `setAuth` (a synchronous Zustand `set` in
  `useAuth.login`/`register`) commits before `navigate`. The observed 401s most
  likely come from the mount effect racing the store update / persist rehydrate
  on the post-auth navigation. The `accessToken`-gated effect fixes the symptom
  regardless of the exact tick ordering; no interceptor change is needed.
- **No retry path chosen:** acceptance offers "gate OR retry once". We pick gate
  (cleaner, avoids a wasted 401 round-trip). The response interceptor's existing
  refresh-on-401 logic is intentionally left untouched — it is for *expired*
  sessions, and adding the gate keeps it from firing spuriously on fresh login.
